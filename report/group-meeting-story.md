# 从 RF-DETR 手机验证到 UniAD 高通部署：组会故事线与实验树

历史规划：2026-09-09，本篇保留当时的组会讲稿与实验树。此后用户已切换到生命周期学习计划并完成 DLC/context/C++ 三路径验证，当前事实以 [生命周期实测报告](lifecycle-results.md) 为准。下文“未做 profiling”“等待权重”等表述是当时状态，不再是当前推进暂停点；PyTorch 精度对齐仍未完成。

## 一句话定位

UniAD 的正式部署受目标开发环境限制，因此先用现有 Snapdragon 8 Elite 手机建立 QNN/HTP 部署验证环境。当前已用 Qualcomm 发布的 RF-DETR small DLC 打通输入准备、设备部署、HTP 执行和输出可视化；下一步补齐正确性与性能证据，再用实际 UniAD 的 MSDeformAttn 子模块验证模型兼容性。

## 组会上可以直接讲的两分钟版本

我们原来的主线是 UniAD 在高通平台上的部署，目前目标开发板和开发环境受限。为了让这段时间的工作能够回到主线上，我把部署问题拆成两部分：一部分是 QNN runtime、HTP、设备通信和输入输出这些公共问题；另一部分是 UniAD 的模型导出、算子兼容和状态管理问题。

现在先利用手头的 S25 Ultra，把第一部分独立验证。选择 RF-DETR small，是因为它是与 Transformer 视觉检测相关的 baseline，而且已经有 Qualcomm 发布的 DLC，可以先控制模型转换这一变量。它与 UniAD 在 deformable attention 方向有技术交集，但并不意味着两者实现可以直接互换。

原先考虑过 AI Hub 云端编译，但账号注册受阻、拿不到 Token，因此当前改用已发布的 DLC，在手机上通过 QAIRT 2.45 的 qnn-net-run、libQnnModelDlc 和 HTP backend 做在线图准备与执行。这条路径目前已经跑通：日志显示 Compose、Finalize、Execute 完成，metadata 记录一次推理成功，输出已拉回并完成检测可视化，也处理了 raw 输出类型和坐标还原问题。

当前成果是一个可复现的手机部署闭环。还没有完成与匹配 PyTorch 权重的对比，也没有可靠的性能统计，所以现在不报精度提升或实时帧率。下一步先解决参考权重来源，补齐正确性验证，再区分启动准备和稳态执行做 profiling。之后从实际 UniAD 代码提取固定 shape 的 MSDeformAttn，用同一套设备流程定位导出和 HTP 支持问题。这样开发环境恢复后，工作可以更集中在 UniAD 本身。

有实际工程价值的细节：本次 classes 的逻辑 dtype 是 int32，但 qnn-net-run 默认把输出文件写成 float。按逻辑 dtype 直接读 raw 会解码错误。这类输入输出约定、日志留存和设备脚本，正是后续模块实验可复用的部分。

RF-DETR 的意义在于提供已发布模型资产的部署 baseline。本次没有自行导出 RF-DETR，也没有单独验证其 deformable attention 的转换过程，不能表述成“已解决 UniAD 的 deformable attention 支持”。

## 后续实验树

标记：✓ 已完成；→ 推荐主干；◇ 需要条件或决策；○ 后续可选。执行顺序仍遵循 memory/PLAN.md。

```text
根：为 UniAD 建立可复现的 Qualcomm 端侧验证能力
│
├─ ✓ 0. 设备执行闭环：RF-DETR small DLC / QAIRT 2.45 / S25U HTP
│    └─ 输入 raw → adb → online prepare → execute → pull → 检测图
│
├─ → A. 正确性基线：输出是否可信？
│    ├─ ◇ 提供匹配的本地 PyTorch 权重及来源/版本
│    │    ├─ 来源可匹配：同图、同预处理、同后处理比较
│    │    └─ 来源不确定：仅作参考，不能把差异归因于 QNN
│    ├─ 小样本场景回归：空场景、密集目标、小目标、不同宽高比
│    └─ ○ 有标注数据且任务需要时：数据集检测指标
│
├─ → B. 性能基线：时间到底花在哪里？
│    ├─ 冷启动：加载 / 图准备 / finalize 与 execute 分开记录
│    ├─ 稳态：预热后重复执行，报告分布及运行条件
│    ├─ 持续运行：观察耗时随时间变化与失败情况
│    └─ ○ 有测量条件后：内存、功耗、温度关联
│
├─ → C. 回归 UniAD：真实 MSDeformAttn 子模块是否能部署？
│    ├─ 从实际 UniAD 版本提取实现、参数、shape 和参考输出
│    ├─ 固定 shape，建立本地参考与导出检查
│    ├─ ◇ 核对本地转换工具和依赖是否齐全
│    ├─ 转换 / 图准备 / HTP 执行，逐层记录成功或失败位置
│    └─ 对照输出、测延迟，形成兼容性矩阵与失败最小复现
│
└─ ○ D. 在已有基线之上的单变量实验
     ├─ DLC → context binary：研究准备开销与资产适配约束
     ├─ 量化：研究误差与执行性能的权衡
     ├─ shape / 模块拆分：研究目标配置与代价
     └─ 第二个模型：确有需要时才抽象公共脚本
```

D 是以后可讨论的方向，涉及新资产路径或工具链时须先明确实验范围，不属于当前 RF-DETR DLC 执行路线的自动扩展。暂不开展 APK/JNI 工程，也不把模型数量作为近期成果指标。

## 主干实验怎么落地

| 阶段 | 要回答的问题与做法 | 可交付成果 / 完成标准 | 依赖与边界 |
| --- | --- | --- | --- |
| A1：同图参考对比 | 固定输入、预处理、类别映射和后处理；先比较候选结果，再比较最终检测。排序不同需按类别和框匹配，不能只逐行相减 | 权重来源记录、对照图、框/分数差异表及差异解释 | 当前缺本地 checkpoint，且 DLC metadata 无 checkpoint 哈希；来源不匹配只能参考 |
| A2：小样本回归 | 用固定本地图片集覆盖不同场景，检查非法数值、越界框、类别与结果可重复性 | 样例清单、逐图结果、异常记录；精度阈值在有可靠参考后确定 | 无标注时不报告 mAP；不自动下载数据 |
| B：性能测量 | 检查本地 SDK 支持的 profiling 能力；区分进程冷启动与同进程重复 execute；建议预热后至少 30 次有效测量 | prepare/finalize 与 execute 分项表，样本数、中位数、P90、范围、失败数及原始日志 | 记录设备状态、电量/充电、温度可观测项和运行配置；adb 总耗时不能当推理延迟 |
| C1：模块参考 | 从实际 UniAD 代码提取 MSDeformAttn，记录版本、输入 shape、dtype 和参考结果 | 可独立运行的最小模块与固定测试输入 | 不用 RF-DETR 实现替代实际 UniAD 模块；需要用户提供或指定代码与依赖 |
| C2：兼容性与性能 | 按导出 → 转换 → prepare → execute → 对比逐步检查，再扩展少量实际 shape | 每个 shape 的状态、误差、执行耗时；失败时保留最小复现和报错 | 单个固定 shape 成功只证明该配置；完整 UniAD 仍有多模块与时序状态问题 |

A 的正确性结论未完成时，B 仍可测“当前 DLC 的执行成本”，但必须注明正确性状态；按现有计划，需用户明确选择跳过权重对比后才推进该分支。当前任务只编写汇报和规划，没有启动这些实验。

## 向领导说明下一阶段承诺

推荐用交付物而非尚无依据的性能目标承诺：

1. 先把“已经跑通”补成“有参考对照、有差异解释”。当前需要手动提供权重与来源；若无法获得，明确记录限制并决定是否先测性能。
2. 再交付一张可复现的性能表，分开准备时间和执行时间，说明波动与测量条件。
3. 随后交付实际 UniAD MSDeformAttn 的兼容性矩阵。成功时给出误差与耗时；失败时给出卡在哪一步、对应配置和最小复现，支持后续改写决策。

完整 UniAD 部署继续是主线目标，但不把它承诺为这轮手机实验的直接产物。手机与后续目标开发板的硬件、系统和 SDK 条件可能不同，迁移时仍需重新验证；可复用的是流程、测试输入组织方式和问题定位方法。

## 常见追问与回答口径

**“这和 UniAD 到底有什么关系？”**

我们先验证共享的 QNN/HTP 执行环境和输入输出流程，再把实际 UniAD 子模块放进同一测试流程。可复用的是设备部署和验证方法；模型算子兼容性仍要单独证明。

**“官方模型跑通，有多少是我们的工作？”**

模型资产来自 Qualcomm。我们的工作是把它接到现有手机上，完成 SDK/runtime 管理、输入准备、在线执行、结果完整性检查与解码，建立能继续换入真实子模块的实验流程。当前属于部署基线建设，还不称为模型或算子创新。

**“现在多少 FPS，精度怎么样？”**

目前只有一次成功执行和单图可视化，还没有稳定延迟和数据集精度证据。下一阶段会分别给参考对比和性能分布，不用命令总耗时推算 FPS。

**“为什么不直接跑 UniAD？”**

直接上完整模型会把导出、算子、运行环境和状态输入问题混在一起。先用现成资产验证环境，再逐个引入真实子模块，能更明确地定位阻塞原因。

**“下一步最需要什么？”**

近期需要 RF-DETR small 的本地权重及可追溯来源，或者决定暂时跳过参考对比、先测性能。进入 UniAD 分支时需要指定实际代码版本、目标模块和输入配置。当前无需新建 Android 应用工程。
